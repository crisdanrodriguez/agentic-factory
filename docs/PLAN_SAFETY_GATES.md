# Plan safety gates before MVP-02

Trusted validation policy `bootstrap-policy-2` is required when a stored plan is approved or started. The PostgreSQL workflow store also compares external-ticket plans with the current project-scoped durable WorkItem revision, full WorkItem content, and source snapshot. These checks run at direct workflow transitions and job authorization, not only through GitHub feedback. Rejection remains available without accepting the plan.

External-ticket approval additionally requires one trusted `ExternalPlanAuthorization` supplied to the workflow store by the owner-controlled composition. It binds organization, project, WorkItem, source digest, profile, exact capabilities/checks/deliverables, and budget ceilings. Starting or authorizing a job also requires its `allowExecution` flag. The current GitHub runtime supplies no such authorization, so external plans fail closed even if a model copies a reviewed command. Model output cannot create this authorization. Wiring owner-managed authorizations is separate work before external software execution.

Model-authored `profile.checks[].command` arrays are assertions only. They must exactly match a reviewed check ID, layer, argv, and environment in the trusted verification registry. A future executor must call `resolveTrustedVerificationCheck` and use only its returned argv and environment; it must never execute the stored model-authored array. The current registry covers only the synthetic Python 3.12 software and ML fixtures. An owner-approved target-project command and environment registry is required before real project checks can run. The registry does not authorize shell interpolation, provider access, or implementation jobs.

The synthetic job adapter distinguishes submission from reconciliation. New submission requires current plan safety, explicit execution authorization, an approved running Run, and no cancellation request. Inspection and cancellation require the authorized project scope, exact persisted job context, and an existing scoped job record. They remain available after authorization revocation, source supersession, policy changes, or Run cancellation. A repeated `start` can return only an already recorded job with the same request digest; it cannot create a job without submission authorization. Fetching a Run for recovery does not itself grant execution.

The policy requires exactly the reviewed checks, capabilities, and deliverables for these two profiles and accepts no model-declared dependencies. Broader project profiles and dependencies require an explicit trusted policy extension. Budgets remain bounded by the policy. Both GitHub `REVISE` feedback and direct external-plan `revise` transitions are disabled: neither can invoke Codex, replace external WorkItem content, or create another Run. A separately designed revision-request workflow is required before enabling either action.

Previously stored Runs are preserved. Plans with `bootstrap-policy-1`, an unknown environment, an unreviewed command, or extra capabilities cannot be newly approved or started under policy 2. In particular, the existing MVP-01B read-only discovery plan remains in `awaiting-approval`; this change neither rejects nor rewrites it. A new owner-reviewed plan revision and a read-only verification profile are separate work. Already submitted legacy jobs remain inspectable and cancellable in their authorized project; recovery cannot authorize a new submission.

These gates establish authorization and provenance of executable checks. They do not establish that a plan's prose is relevant, that a dependency is available, or that reported evidence is scientifically or operationally correct. MVP-02 still needs owner-selected profile constraints, trusted execution wiring, evidence provenance, and human review before any real execution.
