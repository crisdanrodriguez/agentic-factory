## 2. Live scenario matrix

Operator actions below are manual. The adapter enforces the listed automated checks, but it does not generate an acceptance report: the operator must record the expected outcome for each scenario. Read-only database inspection requires the existing authorized observer identity; do not expand the pairing administrator's grants for convenience. Before sending messages, record project-scoped baseline counts for canonical revisions/receipts, workflow Runs, and queue jobs using an authorized read-only observer. Do not start a worker, sandbox, or provider to test absence of side effects. Pace commands beyond the burst of three and below ten per minute; rate-limited commands are consumed without a reply or WorkItem.

| Scenario | Operator action | Existing automated assertion and manual acceptance evidence |
| --- | --- | --- |
| Startup | Start `npm run telegram -- start` with bot configuration. | Adapter verifies database principal/membership, exclusive session lock, TLS, exact bot identity, and absence of a webhook. Stop on failure. Do not delete webhooks or discard pending updates to fix a conflict. |
| Unpaired denial | Expected human sends `/help` in the bot's private chat before pairing. | No reply and no WorkItem. Operator checks counts only. Unauthorized traffic must not create per-sender rows. |
| Issue | With admin configuration, run `npm run telegram -- pair issue PROJECT USER`. Replace placeholders privately with trusted configured values. | Five-minute challenge issued and hash stored; operator views the secret only in a nonrecorded local terminal. Never copy challenge output into evidence. |
| Claim | Human sends the displayed `/start` challenge only to the dedicated bot's private chat. Run `pair show` locally. | Pairing becomes pending, not active. Operator checks chat, generation, expiry and expected human locally; do not publish identifiers. A `/new` before confirmation must create no WorkItem. |
| Confirmation | Run `npm run telegram -- pair confirm USER CHAT GENERATION` with the exact observed trusted values before expiry. | Local confirmation activates only that binding/generation. If expired or mismatched, stop and issue a fresh challenge; never edit pairing rows to bypass the checks. |
| Help | Send `/help`. | Reply contains approved fixed commands and intake limitations only. |
| New request | Send `/new {"objective":"Synthetic development acceptance","context":"Record only. No execution authorized."}` once. | One canonical WorkItem/revision and intake receipt; one update receipt. Operator records only counts and a local opaque test label. No Run, queue wake, approval, provider call, sandbox, or publication. |
| Status | Send `/status ID` using the returned WorkItem ID privately. | ID/revision and recorded-only status; execution explicitly not authorized. No objective/context or source disclosure. Unknown ID returns a generic unavailable response. |
| List | Send `/list`. | At most ten IDs/revisions within the project, no bodies/context. Pagination, where exercised, uses `/list after ID`; do not manufacture extra records solely to fill pages. |
| Unsupported cancellation | Send `/cancel`. | Unavailable response; no execution mutation. |
| Restart after commit | Stop the adapter with SIGINT, wait for exit, restart with the same configuration and retained database. Do not resend `/new`. | Session lock is released/reacquired; existing WorkItem/receipt counts remain unchanged. Queued replies may resume. A reply can duplicate after uncertain delivery; a WorkItem must not. |
| Offline receipt | With adapter stopped briefly, send one additional synthetic `/new`, then restart within Telegram's retention window. | Pending server update is captured and creates exactly one additional canonical request. Restart again without resending; counts remain stable. |
| Revocation | With admin configuration run `npm run telegram -- pair revoke`, then send `/new` and `/status` privately. | Old generation cannot create/read work or send newly attempted queued replies. Counts do not increase. Already committed requests remain; an in-flight reply cannot be retracted. |
| Re-pairing | Only if included in the authorized window, issue a new challenge, claim, and explicitly confirm the new generation. | Old challenge/generation is unusable; the new binding requires operator confirmation. Revoke again before cleanup. |

Duplicate/retry evidence must be described accurately. Telegram assigns a new update ID when a human resends identical text; that is a new request, not a replay. Do not reset cursors, delete receipts, forge updates, alter retry timestamps, or inject faults into the live database to force a demonstration. Exact duplicate replay, first-attempt failure, 60/300-second eligibility, crash-before/after-commit recovery, membership loss, and revocation races remain covered by the maintained deterministic tests. If genuine redelivery or an operational failure occurs during the live window, inspect metadata-only receipts and eligibility, restart without changing them, and verify no duplicate canonical write. If no such event occurs, report it as not observed live rather than claiming live proof.

Delayed processing does not block other eligible updates. A status/list can precede an earlier delayed creation. Three failed attempts exhaust the operation; inspect state/attempts/deadline/failure category without reading payloads. At the 1,000-update cap, stop and report: no pruning, offset advance, or replay workaround. Do not weaken TLS, authorization, or transport limits to complete the checklist.

## 3. Pass/fail criteria and stop procedure

- **Pass:** each required live scenario has its expected observed outcome, canonical counts match the number of distinct accepted requests, no unauthorized writes or execution effects occurred, and cleanup is confirmed. Startup success establishes that the adapter accepted identity/webhook checks; do not claim a live negative webhook test unless a conflict actually occurred. Do not install a webhook to manufacture one.
- **Not observed / incomplete:** a scenario lacks sufficient evidence, including no reply without proof that polling received the update. For denial cases, observe bounded aggregate rejection/cursor metadata and unchanged canonical counts while the adapter remains healthy. Silence alone is not proof of authorization enforcement. Record deadlines agreed for the test window; a timeout is incomplete or failed, never an automatic pass.
- **Fail and stop:** unexpected identity, active pairing before confirmation, unauthorized reply/write, duplicate canonical intake for the same update, sensitive reply, changed permissions, execution side effect, TLS/webhook conflict, exhausted processing, retention exhaustion, or unaccounted state change. Stop sending messages and stop the adapter immediately; preserve redacted metadata and proceed with revocation/cleanup. Do not repeatedly restart to hide a fault or change controls to obtain a pass.
- **Operational rollback:** disable this optional channel by stopping its process, revoking pairing and token, and disabling dedicated development logins. Do not roll back schema migrations, delete receipts, rewind offsets, or erase committed WorkItems. Preserve evidence of a failed run. Recovery or repeat live testing after a failure requires operator investigation and renewed authorization for the changed procedure.

The optional re-pairing and genuine redelivery scenarios may be reported as not exercised. Deterministic duplicate, fault-injection, and concurrency results remain separately attributed to CI. No skipped required live step may be represented as completed acceptance.

## 4. Safe cleanup and retained evidence

Operator intervention is required; no automatic cleanup here grants permission to delete canonical records.

- [ ] Revoke the pairing locally and stop the adapter. Confirm process exit and session-lock release. If PostgreSQL is unavailable, stop the process and revoke the token immediately; complete database revocation after recovery before any restart.
- [ ] Through official BotFather controls, revoke the development token. Do not restart with a replacement token. Record only that revocation was completed, never the token or a screenshot. Bot deletion is optional only with separate owner approval; do not assume deletion erases Telegram's retained data.
- [ ] Remove secret values from process environments, terminal clipboard/history/recordings if accidentally captured, and the temporary secret-manager entry according to the owner's retention policy. Deleting a file is not a guarantee of secure erasure. Any exposure requires token/credential rotation, not just deleting a log.
- [ ] A privileged local database operator disables development logins and terminates only their remaining sessions where necessary. Preserve role identities, memberships, canonical WorkItems/revisions, receipts, digests, and relevant verification metadata. Do not cascade-drop roles or delete shared databases/tables to clean up.
- [ ] Retain synthetic canonical records and backups under private access controls for the agreed review period. Remove only test-owned temporary private configuration/resources after they are no longer needed. Record cleanup failures explicitly; do not claim completion while the adapter can still run or token revocation is unconfirmed.
