# Plan safety gates before MVP-02

Trusted validation policy `bootstrap-policy-3` is required when a stored plan is approved or started. The PostgreSQL workflow store also compares external-ticket plans with the current project-scoped durable WorkItem revision, full WorkItem content, and source snapshot. These checks run at direct workflow transitions and job authorization, not only through GitHub feedback. Rejection remains available without accepting the plan.

External-ticket approval additionally requires one trusted owner authorization from a private file. It binds organization, project, GitHub installation and repository identity, WorkItem, source digest, profile, exact capabilities/checks/deliverables, and budget ceilings. Starting or submitting a job also requires its `allowExecution` flag. The GitHub runtime reloads the file for each decision; omission, removal, or a mismatched replacement fails closed, including for previously approved Runs. Model output cannot create this authorization. See `docs/OWNER_PROJECT_AUTHORIZATION.md`.

Model-authored `profile.checks[].command` arrays are assertions only. They must exactly match a reviewed check ID, layer, argv, and environment in the trusted verification registry. A future executor must call `resolveTrustedVerificationCheck` and use only its returned argv, working directory, environment variables, and fingerprint; it must never execute the stored model-authored array. The registry supports the existing synthetic checks and owner-reviewed external software checks. It does not authorize shell interpolation, provider access, or implementation jobs.

The synthetic job adapter distinguishes submission from reconciliation. New submission requires current plan safety, explicit execution authorization, an approved running Run, and no cancellation request. Inspection and cancellation require the authorized project scope, exact persisted job context, and an existing scoped job record. They remain available after authorization revocation, source supersession, policy changes, or Run cancellation. A repeated `start` can return only an already recorded job with the same request digest; it cannot create a job without submission authorization. Fetching a Run for recovery does not itself grant execution.

The policy requires exactly the reviewed checks, capabilities, and deliverables for these two profiles and accepts no model-declared dependencies. Broader project profiles and dependencies require an explicit trusted policy extension. Budgets remain bounded by the policy. Both GitHub `REVISE` feedback and direct external-plan `revise` transitions are disabled: neither can invoke Codex, replace external WorkItem content, or create another Run. A separately designed revision-request workflow is required before enabling either action.

Previously stored Runs are preserved. Plans with an older policy revision, an unknown environment, an unreviewed command, or extra capabilities cannot be newly approved or started under policy 3. In particular, the existing MVP-01B read-only discovery plan remains in `awaiting-approval`; this change neither rejects nor rewrites it. A new owner-reviewed plan revision and a read-only verification profile are separate work. Already submitted legacy jobs remain inspectable and cancellable in their authorized project; recovery cannot authorize a new submission.

These gates establish authorization and provenance of executable checks. They do not establish that a plan's prose is relevant, that a dependency is available, or that reported evidence is scientifically or operationally correct. MVP-02 still needs owner-selected profile constraints, trusted execution wiring, evidence provenance, and human review before any real execution.
