# Owner-managed external software authorization

`ownerAuthorizationPath` is optional in the private GitHub MVP runtime configuration. It names one absolute, owner-owned, mode-0600 regular JSON file outside source control. The runtime opens it without following symlinks, rejects hard links and oversized or malformed content, binds it to the configured GitHub installation/repository and project scope, and reloads it before each external-plan creation, approval, start, verification, or job submission. An absent file grants nothing. No persistent capability gate is enabled by this setting.

The strict file contract has `schemaVersion: 1`, `policyRevision: "bootstrap-policy-3"`, `scope` (`organizationId`, `projectId`), `repository` (`installationId`, `repositoryId`, `fullName`), `workItemId`, the 64-character durable `sourceSnapshot`, `profileId: "software-general"`, the exact `environment` (`language`, `version`, `fingerprint`), `capabilities`, `deliverables`, reviewed `checks`, budget `limits`, and optional `allowExecution`. Omission of `allowExecution` means `false`. Each check declares its ID, software layer, exact argv, safe relative `workingDirectory`, and environment variables limited to `CI=true`, `TZ=UTC`, and `LANG=C` or `C.UTF-8`. Capabilities and deliverables must equal the mandatory software profile; budget ceilings cannot exceed global limits. Duplicate IDs, shell interpreters, inline-code flags, shell syntax, unknown keys, and environment mismatches fail validation.

The WorkItem origin must identify the same repository. PostgreSQL also checks the current project-scoped immutable WorkItem revision and digest. Approval records a canonical snapshot of the entire owner authorization, including check working directories and the small fixed set of permitted nonsecret environment variables. Any change requires a new revision-bound approval before execution; revocation blocks new submission while scoped inspection and cancellation of an existing job remain possible.

This is a declaration and approval gate, not an executor. The argv validator conservatively rejects common inline-code flags, including joined short and long forms; argv validation alone does not make executing repository code safe. MVP-02B must establish a reviewed checkout/workspace identity, verify the working directory and executable at runtime, provide a clean environment, use direct argv without a shell, bind a sandbox grant to the current Run, enforce runtime limits, and record check evidence. This increment does not clone a repository, invoke an agent, run checks, or enable external execution.
